# 部署记录与踩坑

按教程部署过程中遇到并解决的问题，供复现时参考。

## 0. 环境

* WSL2 Debian 13 (trixie)，开 systemd
* Node **v6.9.5**（`/opt/node6`，软链到 `/usr/local/bin/node`）
* MariaDB 11.8（替代教程里的 MySQL 5.6）
* nginx 81，C++ 服务见 README

## 1. WSL 没有 init / systemd

Debian 镜像是最小 rootfs，**没有 systemd**：

```bash
apt-get install -y systemd systemd-sysv
printf '[boot]\nsystemd=true\n' > /etc/wsl.conf
wsl --shutdown    # Windows 侧执行
```

否则 `[boot] systemd=true` 不生效，PID 1 仍是 `init(Debian)`，服务无法开机自启。

## 2. MySQL 5.6 → MariaDB 11

* `lower_case_table_names=1` 必须在**初始化前**写进配置（见 `deploy/mysql/99-fyqst.cnf`）
* 老 dump 里有零日期，必须 `sql_mode=''`，否则导入报错
* root 默认走 `unix_socket` 认证，需改成密码认证并补 `root@127.0.0.1`（`deploy/mysql/01_root.sql`）

## 3. PHP 5.6 无法安装 → PHP 层整体 C++ 化

Debian 13 没有 PHP 5.6，且这批 PHP 用的是 `mysql_*` 老 API。
方案：用 C++（cpp-httplib + MariaDB C API）1:1 重写 `game.php` / `pay.php` / `cdkmail.php` /
`gm/*` / `cdk/*`，nginx 只把 `*.php` 反代到 127.0.0.1:9500。
原 PHP 源码移到 `/www/_php_orig`，web 根目录 `.php` 文件数为 0。

## 4. 客户端卡在 52/54（进不了游戏）★

**现象**：登录后加载进度停在 52/54、53/54，每秒向 `/bi` 上报一次，一直进不去。

**排查**：

1. nginx 访问日志：页面只加载到 `pay_sdk.js` 就停了，没有后续资源请求；
2. `/bi` 参数里能看到登录其实成功（`accountId/userId/serverId` 都有），说明卡在取版本清单之后；
3. `ss` 显示客户端只连着 `:81` 和 `:9902`，**完全没有连 9901/20001/10001**。

**根因**：页面在 `:81`，清单在 `:9902`，属于**跨源请求**；`/manifest` 响应没有
`Access-Control-Allow-Origin`，浏览器把响应扣住，客户端 XHR 永远等不到数据。

**修复**（`src/fyversion.cpp`）：

* 所有响应加 `Access-Control-Allow-Origin: *`，并处理 `OPTIONS` 预检；
* 额外把 `/resource` `/libs` `/js` `/css` 也挂到 9902（以防客户端把清单地址当资源根）；
* 增加 `/Server/startlog/version_access.log` 请求日志。

修复后客户端顺序上报 `start → load_picture → welcome(进游戏)`，nginx 开始大量返回
`resource/dynamic2/map_*.jpg`，`ss` 显示已与 20001/10001/9901 建立连接。

## 5. 主城服监听空端口（`city listening on *:`）

**根因**：`uc` / `s1` 下多个 Node 进程共享同一个 `config/project.json`，而每个
`env-cfg/*.js` 只声明自己的端口，`reset.js` 会把其它端口写成空串，**后启动的进程覆盖前面的**。

**修复**：`deploy/scripts/fix_ports.py` 给 14 个 `env-cfg/*.js` 追加端口兜底
（9901/9902/9903/10001/20001/9001/7000），任何进程写出的 `project.json` 都是完整端口集合。

> 注意：追加代码前必须有分号，否则 `}(function(){...})()` 会被解析成函数调用而报
> `(intermediate value)(...) is not a function`。

## 6. Windows 启动脚本报 `'exe' 不是内部或外部命令`

**根因**：`.cmd` 文件用了 **LF 换行**，cmd.exe 解析错乱。

**修复**：保存为 **CRLF + 纯 ASCII**（中文会受代码页影响），并避免文件名带空格。
仓库里的 `deploy/start_fyqst.cmd` 已按此处理，`.gitattributes` 保证 `*.cmd` 检出为 CRLF。

## 7. Node 6 原生插件不需要 node-gyp

Debian 13 没有 python2，`node-gyp` 起不来。但 Node 6 的头文件就在 `/opt/node6/include/node`，
可以直接编译：

```bash
g++ -shared -fPIC -O2 -std=c++11 -I/opt/node6/include/node -o fynative.node fynative.cpp
```

生成的 `.node` 通过 `require('fynative')` 加载，JS 侧用 try/catch 兜底，加载失败自动回退纯 JS。

## 8. WSL 空闲自动关机

WSL 在没有会话时会关停发行版，服务随之停止——这正好符合"打开 WSL 才跑、关掉就停"的预期。
不要装常驻保活脚本，否则会一直占内存。需要玩的时候保持一个 WSL 窗口开着即可。

## 11. 性能实测：keep-alive 下的 TCP delayed-ACK 陷阱（54× 提升）

### 现象

用 `ab -k` 压测 C++ 服务，每请求固定 43~45 ms，吞吐只有 ~1,100 req/s，而 CPU 只占 12%（明显不是算力瓶颈）。

### 定位

| 场景 | fyversion 吞吐 | 每请求延迟 |
|---|---|---|
| keep-alive（`-k`） | 1,102 req/s | 43.4 ms |
| 每次新连接 | **19,050 req/s** | — |
| Node 9901（对照） | 1,308 req/s | 0.94 ms |

同一代码，**不开 keep-alive 快 17 倍** → 不是计算问题，是 TCP 层：
服务端把响应头和 body 分两次 write，对端 delayed-ACK 40ms，Nagle 又等着 ACK 才发下一个包。

### 修复

`cpp-httplib` 默认不开 TCP_NODELAY，编译时加宏即可（`Makefile`）：

```make
CPPFLAGS ?= -I/usr/include/mariadb -DCPPHTTPLIB_TCP_NODELAY=1
```

### 效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| fyversion `/manifest` 吞吐 | 1,102 req/s | **59,211 req/s**（54×） |
| 单请求延迟（串行） | 43.4 ms | **0.081 ms** |
| P99 | 48 ms | 3 ms |

> 这个 bug 会真实影响客户端：浏览器访问 `:9902/manifest` 就是 keep-alive，
> 修复后客户端启动加载明显更跟手。

### 顺带

* 访问日志改为内存缓冲批量落盘（`src/logbuf.h`），避免每请求 fopen/fclose；
* 结论：**在讨论多线程之前，先确认延迟是算力问题还是协议问题**——本例中前者不是。
